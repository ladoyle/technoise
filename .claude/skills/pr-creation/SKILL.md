# The problem

`gh pr create` and the GitHub MCP server's PR-write tools (`pull_request_write`,
`create_pull_request`) route through GitHub's GraphQL API. In this environment, that path
has failed consistently across many independent agent runs — every documenter cycle observed
in this repo's bugfix history hit it — with an error like `GitHub GraphQL is not available
from Claude Code sessions` or an HTTP 403. This is despite the same MCP server's *read* tools
(`pull_request_read`, `issue_read`, `list_issues`, …) working normally in the same context,
and despite a top-level orchestrating session sometimes being able to create a PR directly
with `mcp__github__create_pull_request`. Subagents dispatched via the `Agent` tool have hit
the block every time it's been tried.

Don't spend a round trip rediscovering this. If you're opening a PR from inside a subagent
(developer, documenter, gatekeeper), go straight to the REST fallback below rather than
trying `gh pr create` first and waiting for the same failure.

# Procedure

1. Push the branch first — REST PR creation needs the branch to already exist on the remote:

   ```sh
   git push -u origin <branch-name>
   ```

2. Check for a PR template (`.github/pull_request_template.md`,
   `.github/PULL_REQUEST_TEMPLATE/`, root `PULL_REQUEST_TEMPLATE.md`,
   `docs/PULL_REQUEST_TEMPLATE.md`) and mirror its sections if one exists.

3. Write the PR body to a temp file. Never inline a multi-paragraph markdown body into a
   shell `-f` flag — PR bodies routinely contain backticks, `$`, quotes and blank lines that
   break shell quoting silently instead of loudly:

   ```sh
   cat > /tmp/pr-body.md << 'EOF'
   ## Summary

   ...

   Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
   Claude-Session: <session-url>
   EOF
   ```

4. Create the PR via the REST API directly, bypassing whatever GraphQL-backed path just
   failed:

   ```sh
   gh api repos/<owner>/<repo>/pulls \
     -f title="<concise title>" \
     -f head="<branch-name>" \
     -f base="master" \
     -F body=@/tmp/pr-body.md
   ```

   `-F body=@<file>` reads the body from a file rather than the shell argument list — that's
   what actually avoids the quoting problem. `-f body="$(cat file)"` still passes through the
   shell and can still break on the same characters.

5. Confirm the PR actually exists before reporting success — read it back rather than
   trusting the create call's exit code:

   ```sh
   gh api repos/<owner>/<repo>/pulls/<number>
   ```

   or the MCP `pull_request_read` tool (`method: "get"`), which has been reliable for reads
   throughout. Check `state`, `mergeable_state`, and that the title/body landed as written.

6. If a **write** MCP tool is confirmed available and working in the current context — verify
   with a real attempt, not by assuming from the tool list — prefer it over `gh api`. It's
   tried second here only because the GraphQL path has repeatedly failed and the REST fallback
   is what's actually been dependable.

# Notes

- This block has not been observed on other GitHub write operations in this repo's history —
  issue creation via `issue_write`, review comments, and `add_issue_comment` have all worked
  normally. It appears specific to PR creation. Don't pre-emptively route other GitHub writes
  through this fallback without first confirming they actually fail.
- `gh pr create` fails the same way for the same reason — it's a thin wrapper over the same
  GraphQL mutation. Skip straight to step 4 rather than trying it first.
- Every PR body must still end with the repo's required attribution trailer per the root
  `CLAUDE.md`/`AGENTS.md` git rules. Writing it into the temp file in step 3 gets it right
  byte-for-byte, since nothing re-escapes it on the way to GitHub.
- GitHub Pages, GitHub's own UI, and any other GitHub App may still append their own footer
  (e.g. a "Generated by Claude Code" line) after the PR is created — that's additive, not a
  sign the body was mangled.
